# 01. 연구 주제 후보와 선택 근거

> **최종 선택: A + E (장기기억 페르소나 챗봇 + 한국어 페르소나 평가 벤치마크)**
>
> 엔터테인먼트 도메인에서 "AI 아티스트 페르소나 챗봇"을 주제로 잡고, 실현 가능한 연구 주제 8개를 비교한 뒤 두 개를 결합해 선택했다.
> 왜 기록하는가: 주제를 왜 이렇게 좁혔는지가 프로젝트의 설계 판단을 설명해 주기 때문이다.

## 도메인 문제 정의

AI 아티스트 챗봇이 실제 팬 서비스로 성립하려면 다음이 동시에 필요하다.

1. 일관된 페르소나(세계관·말투)를 유지할 것
2. 팬 개개인을 세션을 넘어 기억할 것 (이름, 선호, 지난 대화)
3. 그 품질을 사람 감이 아니라 수치로 측정할 것

1과 2는 stateless LLM의 구조적 약점이고, 3은 한국어·엔터 도메인에 공개 벤치마크가 거의 없다. 이 세 가지가 주제 선택의 기준이었다.

## 후보 8개 비교

| # | 주제 | 핵심 기술 | 난이도 | 예상 기간 | 24GB GPU 1장 |
|---|---|---|---|---|---|
| **A** | 장기기억 메모리 아키텍처 기반 아티스트 페르소나 챗봇 | RAG, 메모리 계층, LangGraph, MCP | 상 | 4~6개월 | 가능 (7~8B 추론) |
| B | LoRA/QLoRA 파인튜닝으로 아티스트 말투·페르소나 학습 | PEFT, TRL | 중상 | 3~5개월 | 가능 (QLoRA 7B) |
| C | MCP 툴 사용 팬 상담 에이전트 (스케줄·앨범·굿즈 조회) | MCP, tool calling | 중 | 3~4개월 | API 중심, 최소 |
| D | 저지연 챗봇·음성 파이프라인 최적화 (양자화·vLLM·스트리밍 TTS) | vLLM, FP8/AWQ | 상 | 4~6개월 | 부족, 클라우드 필요 |
| **E** | 한국어 페르소나 일관성·환각 품질 평가 벤치마크 | LLM-as-judge, RAGAS, PICon | 중 | 3~4개월 | 경량 |
| F | MLOps 지속 개선 루프 (피드백 → 평가 → 재학습 → 배포) | MLflow, 자동 LoRA 재학습 | 중상 | 4~5개월 | 재학습용 필요 |
| G | 멀티채널·감정·팬 맥락 인식 응답 모듈 | 감정 분류 + 조건부 생성 | 중 | 3~4개월 | 중간 |
| H | 유저 시뮬레이터 기반 페르소나 스트레스 테스트 / 세계관 RAG | LLM 시뮬레이터, lore RAG | 상 | 4~6개월 | 중상 |

## 각 주제 한 줄 요약

- **A. 장기기억 페르소나 챗봇**: 단기 버퍼 + 에피소드 메모리 + 사실 메모리를 결합해 수십 세션에 걸친 팬 기억을 유지하는가. LongMemEval 원 논문은 상용 챗봇이 장기 세션에서 약 30% 정확도 하락을 보인다고 보고해, 개선 효과를 보이기 좋은 난이도.
- **B. 페르소나 파인튜닝**: 프롬프트·RAG 대비 LoRA가 말투 일관성에서 얼마나 나은가. PICon 연구는 프롬프트 기반이 오히려 더 일관적일 수 있다고 보고해 검증 가치가 있음. 다만 실존 아티스트 말투 학습은 퍼블리시티권 문제.
- **C. MCP 팬 상담 에이전트**: 콘서트 일정·앨범·굿즈를 툴로 조회해 환각 없이 답하는가. 데모가 명확하지만 실제 아티스트 데이터 API가 없어 모킹 의존.
- **D. 저지연 파이프라인**: 양자화·vLLM·스트리밍 TTS로 first-token 지연을 어디까지 줄이는가. 하드웨어 비용과 실존 목소리 사용 불가 문제.
- **E. 한국어 평가 벤치마크**: 페르소나 일관성·환각·사실 회상을 자동 평가하고 judge가 사람 평가와 얼마나 정렬되는가. 한국어·엔터 도메인은 공백 영역이라 논문화 가능성이 가장 높음.
- **F. MLOps 개선 루프**: 장기 운영 시 페르소나 드리프트를 재학습 루프가 얼마나 억제하는가. 실서비스 로그가 없어 시뮬레이션 의존.
- **G. 감정·채널 인식 응답**: 팬의 감정과 채널(채팅/음성)에 맞춰 응답 스타일을 바꾸면 만족도가 오르는가. 감정 라벨의 주관성이 리스크.
- **H. 유저 시뮬레이터 평가**: LLM 팬 시뮬레이터로 대규모 스트레스 테스트를 하면 정적 벤치마크가 놓치는 페르소나 붕괴를 잡는가. 시뮬레이터 신뢰도 자체가 연구 쟁점.

## 왜 A + E 인가

- **시스템 + 벤치마크 구조**: A로 만든 것을 E로 측정하면 "구현물과 평가축"이 한 편의 논문 구조가 된다. A만 있으면 데모에 그치고, E만 있으면 측정 대상이 없다.
- **자원 제약에 맞음**: 둘 다 24GB GPU 한 장 또는 API 호출로 실험이 끝난다. D·F는 하드웨어, B는 데이터 권리 문제가 선행돼야 한다.
- **부트캠프 모듈과 직결**: RAG → Agent → MCP → 평가 순서가 A+E 구현 순서와 일치한다 (docs/03 참조).
- **윤리 리스크가 가장 낮음**: 가상 아티스트를 직접 설계하면 실존 인물의 말투·목소리·초상 문제를 피할 수 있다. B·D는 이 문제를 피하기 어렵다.

## 비교 조합 (검토했으나 보류)

- **B + E**: PEFT 직결이지만 한국어 아티스트 말투 데이터 확보가 선행 문제. A+E 완료 후 확장 과제로 보류.
- **D + F**: 엔지니어링 임팩트는 크지만 GPU 예산과 실서비스 로그가 없어 10주 안에 결과를 내기 어려움.

## 확장 방향

- A+E가 끝나면 B(로컬 모델 LoRA로 페르소나 말투 학습)를 비교군으로 추가한다.
- H(유저 시뮬레이터)는 E의 평가셋 합성 단계에서 부분적으로 차용한다.

## 주의사항

- 메모리 프레임워크(Mem0 등)가 발표하는 LoCoMo·LongMemEval 고득점은 벤더 자체 평가이며 프로토콜이 달라 직접 비교가 부적절하다. 이 프로젝트는 동일 프로토콜로 비교군 4종을 직접 돌린다.
- 실제 K-pop 아티스트 대화·목소리 데이터는 저작권·초상권·퍼블리시티권 문제로 사용하지 않는다. 공개 데이터와 합성 데이터로만 진행한다.
